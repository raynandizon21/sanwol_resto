# ZKTeco MB160

Read `docs/zkteco-mb160.md` first (architecture, file map, `.env` keys, device settings, schema, firmware findings, the cloud/network move checklist and the roadmap), and `docs/attendance.md` for attendance (hours from time-ins and time-outs; optional schedules for late, undertime and absences; holidays, day marks and per-branch cutoffs; no overtime), employee profiles and manual punches. Its last section lists what was planned but not built (overtime, payroll).

Rules that keep it working:

- **Device endpoints:** `/iclock/*` lives only on the separate listener (`server/services/admsServer.js`, port `ZK_ADMS_PORT`), never on the main API. The device cannot log in, send CSRF tokens or follow redirects.
- **Acknowledgements:** reply `OK: <lines>` only after the DB commit. On failure, answer HTTP 500 so the device resends. Keep punches unique on `(DEVICE_ID, PIN, PUNCH_DT)`.
- **Keep in sync with zkteco_test:** `server/services/admsService.js` is a port of `zkteco_test/src/Adms.php`. When protocol handling changes, update both or note the divergence in the doc.
- **Times:** punch times are device-local text. Don't convert them through JS `Date` or the server timezone. Device code uses `config/zktecoDb.js` (main DB, `dateStrings`, `time_zone = +08:00`), not `config/db.js`.
- **Sensitive data:** biometric payloads are never stored (only metadata + `TEMPLATE_HASH` in `zk_biometric_templates`; `zk_raw_requests` bodies are redacted by `redactBody`). No API returns `employee.ZK_PASSWORD` or `ZK_CARD_NO`; never `SELECT e.*` from employee in an API.
- **Punches:** all punches are in `zk_attendance_logs` (`SOURCE` device/manual). A device punch's own fields (`PIN`, `PUNCH_DT`, `PUNCH_STATUS`, `RAW_LINE`) are never changed: edits go in `PUNCH_DT_NEW`/`PUNCH_STATUS_NEW`, deletes in `IS_DELETED`. Read time via `EFFECTIVE_DT` (generated, indexed) and status via `COALESCE(PUNCH_STATUS_NEW, PUNCH_STATUS)`, skip `IS_DELETED = 1`. `EMPLOYEE_ID` is set on arrival (`punchOwner`) and only changed by the NULL backfill in `saveUser` or by `mergeIntoFormerEmployee`.
- **Schema style:** follow sanwol_resto conventions (snake_case tables, UPPERCASE columns, `IDNo`, `*_ID`, `*_DT`, `ACTIVE`, `ENCODED_*`/`EDITED_*`). **Naming: tables of the ZKTeco integration start with `zk_`, columns it adds to existing tables start with `ZK_`** (plus `ZKTeco MB160: …` / `ZKTeco: …` comments). Everything is in sanwol_resto, so join `employee`, `branches` and `user_info` directly. Use `utf8mb4_general_ci` (mixed collations break PIN comparisons).
- **Testing:** test protocol changes by replaying `zk_raw_requests` or hand-written device lines into a scratch DB (see the doc), not by posting fake data with the real serial number `ECV3262300063`.
- **Changes and live events:** emit `emitZkChange` only after the transaction commits, so open pages never re-fetch half-written data. Queue device commands through `AdmsService.queueCommand`. Never return raw `zk_device_commands.COMMAND` (it can contain the device password).
- **New-row detection:** don't use `affectedRows` from `INSERT … ON DUPLICATE KEY UPDATE` to tell whether a row is new; mysql2's `CLIENT_FOUND_ROWS` makes unchanged rows report 1 too. Use `INSERT IGNORE`.
- **Device data on first connect:** a device that already uploaded elsewhere ignores `Stamp=None`. Its existing users and punches have to be requested with `DATA QUERY USERINFO` / `DATA QUERY ATTLOG` (done automatically on first connect).
- **Enrollment:** fingerprints can be enrolled remotely (`ENROLL_FP`); faces can't on this MB160 firmware. For `ENROLL_*` only `Return=0` is success. Unclaimed enrollments expire after 2 minutes so an offline device never prompts later. Only one enrollment runs per device at a time. The device rejects re-scanning an enrolled finger (Return=4, even for the same user), so re-enrolling means `DATA DELETE FINGERTMP` first.
- **Cards:** 125 kHz EM only (NFC/Mifare isn't read). There's no remote card prompt: `ENROLL_CARD` and 30+ other guessed verbs → -1002 (list in the doc), and `ENROLL_MF` returns 0, shows nothing, then silently waits ~65 s for a Mifare card that never registers. An unregistered swipe sends nothing. So cards are added and removed at the device, like faces (the device sends the USER line with `Card=` only once the admin exits the user's menu; removing one sends only `OPLOG 12`). Don't bring back a guided card dialog or a typed card-number field.
- **What the app manages (since 2026-11-04):** the restaurant uses fingerprints. Add employee always sends a regular user (Pri=0) with no password. The device name is never typed: it follows the profile name (`services/deviceNameSync.js`, run on profile save). The app manages fingerprints; role (admins), password, card and face are set on the MB160 only, and the server ignores those fields if sent. The app sets only Time-in/Time-out punch types (an edit may keep a punch's current type).
- **Editing users:** `DATA UPDATE USERINFO` replaces the whole record. Edits (renames) must carry the current Pri, Card, Passwd, Grp, TZ and Verify (`buildUserUpdateCommand`); the add command (`buildUserUpsertCommand`) sends an empty card and password and would wipe them.
- **Add employee details:** profile fields ride on the add command (`zk_device_commands.PROFILE_JSON`) and become the employee row when the device confirms (`applyCommandResult` → `saveUser`, one transaction). Nothing is written to `employee` before that. Clear `PROFILE_JSON` on every way an add can end without success. Device names come from `deviceNameFor` (server `utils/employeeProfile.js`, mirrored in `profileFields.tsx`): always ≤ 24 characters.
- **A device user is an `employee` row:** removing them never deletes it; every removal path (app delete, OPLOG 103, full sync) uses `REMOVE_FROM_DEVICE_SQL` (`ZK_ON_DEVICE = 0`, password/card erased, templates deleted). One person per User ID per device (`ZK_ACTIVE_PIN`); a PIN reused on the device is a new employee row; only Add again (`zk_device_commands.EMPLOYEE_ID`) or Returning employee puts a removed person back. Look up "who has this PIN" by `ZK_DEVICE_ID` + `ZK_ACTIVE_PIN`, and a punch's person by `zk_attendance_logs.EMPLOYEE_ID`. One device per employee.
- **Mirror:** after a successful `DATA QUERY USERINFO`, people not reported since the query was sent are taken off the device and their templates deleted (`ZK_SYNCED_DT` / `SYNCED_DT`). Keep those set on every report and `ZK_EDITED_DT` / `EDITED_DT` for real changes only; otherwise the mirror deletes real data or the timing checks drift.
- **Testing against the live device:** commands contain real tab characters. Shell heredocs in this environment can mangle `\t`, so write command strings in files or with `CHAR(9)` in SQL. A literal `\t` once created a user whose PIN was the whole command line.
- **Editing this code with the dev server running:** nodemon restarts on every save and the device keeps posting, so a half-edited model can create tables/rows with the old design. For schema changes, stop the server or write the model first.
- **Docs:** after changing device settings, env keys or tables, update `docs/zkteco-mb160.md`.
